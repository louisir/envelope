# 首版 VPS 主备中继协议与故障语义

版本：1.1｜日期：2026-09-20｜状态：目标协议，待实现、待验收。1.1 与主设计 HA-D1 对齐组件、控制恢复代际和跨传输接收结果签名边界；可靠性门槛不变。

用户已同意先落实协议与验收标准。本文将“P2P 优先、VPS 主备兜底、离线信封保留”作为首版中继范围；参数为本版提出的可执行验收基线，尚非实测结果。当前源码行为见 [现有设计](design.md)，验证门槛见 [主备验收标准](relay-ha-acceptance.md)。

## 1. 范围与承诺

保留双方 P2P、独立离线密封/拆封、单聊、文件和已有群组逐收件人信封能力。VPS 提供身份/路由登记、密文 mailbox、领取、结果回执、在线互加会话和固定主备节点发现。客户端不为第三方转发或代存。DHT、跨运营方自动互联、开放加入、多来源客户端目录传播、动态扩容和全网负载分配不属于首版门槛。

首版保证：在有效保存期限内，已经收到 `replicated` 确认的未交付信封，任一业务节点单独故障或永久丢盘后，仍能由另一完整副本恢复；重复投递不会产生重复的业务入库/群控制应用。服务器只能验证自身存储和收件方签名，不宣称能审计收件人设备是否诚实。

边界：不承诺两份业务数据同时丢失后的零丢失；不承诺无多数派、无可达节点、网络无限延迟时的自动恢复时限；移动系统暂停应用期间不承诺即时后台到达；到期、用户主动清除客户端数据及保存期限外的灾难恢复单独处理。备份仍然必要，复制不是备份。

故障模型为受管节点的停机、存储错误、进程暂停和网络分区；节点私钥/控制面被攻破属于另行处置的安全事件，不将多数派协议宣传为抵抗恶意运营者的拜占庭容错。端到端加密与联系人验证仍独立于服务器可信程度。

## 2. 角色与唯一写入权限

目标拓扑为两台业务节点 S1/S2，加第三故障域 Q 上的仲裁成员。S1/S2 各保存完整业务副本；控制面由 S1/S2/Q 的三个 etcd 投票成员提供多数派，业务数据沿用独立 SQLite。Q 仅保存控制及签名结果元数据，不保存信封正文，也不是第三份业务数据副本。具体模块、Txn fencing、准备日志和恢复流程见 [主设计第 16 节](design.md#16-首版主备实现设计--first-release-ha-implementation-design)；当前未部署。

- `cluster_id`：受管集群身份；`config_epoch`：已授权成员配置版本；`leader_term`：控制面单调递增的主节点任期；`commit_index`：正式提交顺序；`node_incarnation`：节点数据代际。上述标识不得混用。
- `control_generation`：管理员签名的控制面灾难恢复代际；任期仅在同一代际比较，恢复旧控制快照不能让客户端接受同代际回退。正常选举不增加该代际。
- 稳态只有一个主节点可以提交权威业务变更。备用可返回签名的发现、角色与健康信息，但不能独立接受正式写入或声称最新 mailbox 为空。
- 多数派确认主节点资格，新主必须具备全部既有提交所需的数据，并应用至控制面提交水位后才能服务。仲裁不能将空节点或旧快照直接升主。
- 每项正式提交都必须原子校验当前任期/配置并取得控制面的持久提交决定；只在进程启动时检查租约不够。过期任期的准备、提交、删除和状态更新必须拒绝；暂停后恢复的旧主也不例外。
- 正式 mailbox 读取和状态查询必须经过当前主节点的线性一致读屏障，确保应用至对应提交水位。失去多数派时不能把旧缓存当作最新结果。已收讫的历史签名证据可供核验，但不是当前领导权证明。
- 控制面提交顺序与业务双副本持久化是两个条件：S1+Q 的多数派不能替代 S2 的业务数据落盘。
- 不自动抢回最初的主角色。恢复节点先补齐并作为备用；计划回切采用维护流程，客户端不因“原主恢复”立即跳回。

若实施方案仅有两个故障域而没有等效可验证的仲裁/隔离机制，则不能通过本文的自动升主及网络分区用例。组件和存储适配路线已在 HA-D1 定义；编码须按其验证 fencing、双落盘和恢复，不能仅以 etcd 安装成功声称本节已满足。

## 3. 安全不变量

| 规则 | 必须一直成立 |
| --- | --- |
| I-01 | 没有双业务副本持久化证据及有效提交决定，不返回 `replicated` |
| I-02 | 已正式提交且未到期/未终结的数据，在单业务节点故障后不会因切换丢失 |
| I-03 | 只有当前有权主节点提交正式变更；旧任期不能覆盖新状态 |
| I-04 | 相同信封 ID、收件人及内容只应用一次；相同键不同内容必须冲突，不能后写覆盖 |
| I-05 | `delivered` 只来自收件方签名的业务接收结果，不来自上传成功、HTTP 200、队列删除或坏信封 ACK |
| I-06 | 客户端在失去可恢复副本之前必须已有双副本保存证据或收件方确认；降级状态不能静默清理 outbox |
| I-07 | 终态和删除标记先持久化再清理正文；旧节点、旧快照、迟到副本不能复活消息 |
| I-08 | 无法满足安全前置时显式排队/降级/拒绝，不通过放松验签、TLS、任期或数据水位获得“成功” |

## 4. 信封状态、UI 与副本保留

存储状态和投递结果使用两个字段，不把它们压成一个可任意回退的字符串。现有 `server_mailbox`/`delivered` 显示需适配，不能直接沿用其旧解释。

| 字段 / 值 | 含义 | 客户端行为 |
| --- | --- | --- |
| `storage_state=local_pending` | 发送事务已在本地持久化，尚无服务端保存证据 | 显示待发送；重启恢复原 ID/密文 |
| `storage_state=staged_single` | 一个业务节点持久化暂存，但未双副本正式提交 | 显示等待可靠保存/服务降级；保留 outbox 并重试 |
| `storage_state=replicated` | 主备正文、必要元数据及幂等索引均已持久化，并存在合法提交决定 | 显示已可靠保存，等待接收；首版仍保留 outbox 至投递终态或有效期结束 |
| `delivery_state=pending` | 无收件方业务接收结果 | 不能显示已送达或已读 |
| `delivery_state=deferred` | 收件方已持久保存因果等待项，尚未业务应用 | 显示等待处理；服务器正文继续保留 |
| `delivery_state=delivered` | 收件方解密、验签，完成内容/文件及必要状态的本地持久事务，签署结果 | 显示已送达；不表示用户已读 |
| `delivery_state=rejected` | 收件方确定性拒绝，如未知联系人/坏密文，并签署拒绝结果 | 显示未送达及可解释原因；不能转成 delivered |
| `delivery_state=expired` | 当前主节点已提交到期处理，且没有更早的有效接收证据 | 显示保存期限已过；重新发送是显式新操作 |

客户端不得因暂时查询不到记录将 `replicated` 降成“发送失败”或自动产生新 ID；进入结果待确认并按原 ID 对账。网络恢复后允许基于可验证的新证据推进状态。先收到 `expired` 后拿到“到期前已本地入库”的收件方签名结果，可经主节点核验后改为 delivered，保存二者时间线，不能伪造新的到期后接收时间。

收到存储响应丢失时仍用原 ID/密文/hash 重试。重签请求时间戳不改变逻辑 ID、接收方、正文、hash 或固定到期时间。群组按每收件人统计；部分成功不显示整群送达。文件只有全部分片校验并原子形成可用文件、元数据入库后才出业务 delivered，分片收到不等于整个文件送达。

首版不新增已读回执。P2P 的业务确认同样须在接收端持久化后签署；要区分实际 direct、Iroh 等传输中继、Envelope mailbox。离线导出不表示送达，网络失败也不自动向第三方工具发送文件。

## 5. 需要同步的数据与提交语义

正式复制单元应是有序业务事务，而非无关联地轮询各张表。事务记录包含操作 ID、集群/配置/任期、顺序、类型、对象键、规范化内容 hash、依赖版本、固定到期时间和原始授权证明。

| 数据 | 复制要求 |
| --- | --- |
| Contact、设备登记与路由 | 先验证身份授权；路由及其验证所需的公开身份原子可见，版本冲突拒绝，不靠不同机器的墙钟决定胜负 |
| mailbox 正文、hash、TTL、幂等记录 | 同一事务；重试不能更新 TTL 或替换正文 |
| 接收结果与删除标记 | 保存收件方签名、结果类型和原因；结果提交与 tombstone 原子关联 |
| intro 发布、响应、过期与消费状态 | 同步 owner/responder bundle 及全部状态，切换后继续同一 session；有期限/重复响应约束 |
| 幂等结果、已提交水位、恢复代际 | 保留重试结果，恢复时不能只复原业务表却沿用错误游标 |
| 集群配置与主角色 | 由控制面管理并授权；不作为无约束的普通表合并 |

双副本提交的必需阶段：

1. 验证用户/节点授权、配额、对象版本与当前任期；对重复 ID 返回既有结果，不同内容返回冲突。
2. 将准备记录和正文分别写入两个业务节点的持久日志/存储，校验 hash 和事务依赖，取得两个独立节点的落盘确认；内存接收或仅写 socket 不算。
3. 控制面原子核对任期、配置、对象版本及双副本证据，持久化提交决定和顺序。控制记录至少能关联对象键、操作 ID、内容 hash、数据代际与落盘节点，不含正文。
4. 业务节点依据决定幂等应用、推进提交水位；主节点应用完成后才能对外返回签名的 `replicated` 结果。备用升主前必须补应用，不能把“已经保存准备记录”当作“已经可读”。
5. 在任何步骤崩溃后按持久决定恢复：无决定的准备记录不能自动成为正式写入；有决定的数据必须应用，响应丢失通过查询或同 ID 重试恢复。

HA-D1 选择 SQLite WAL/FULL 的持久准备/业务事务，结合 etcd Txn 提交决定。该适配仍需实现和验证；不能把定时 `POST /v1/nodes/sync` 直接认作此提交协议。必须测真实落盘语义和崩溃点。不得跨主机共享同一 SQLite WAL 文件。

## 6. 单副本降级与接收确认

只有一个业务副本但该节点拥有有效主角色、多数派和完整历史时，允许返回 `staged_single`，并向在线收件人提供不可变的已验证信封；不得返回 replicated。新登记/路由只能作为当前任期有时效的暂存状态，客户端保留签名源资料并重登，不宣称高可用提交。intro 在降级期间返回可重试不可用；已完整复制的 intro 可读，但新响应需双副本才能确认，离线 Contact 交换仍可用。

收件人收到降级信封后仍可本地持久化并签署 delivered。只要发送方验证并保存该结果，可以终结发送；此时确认依据是接收端的持久副本，不是服务端双副本。主节点可在控制面有序记录暂存/结果摘要并转送结果；有序接受的接收结果优先于后续同 ID 重传，不允许为已接收项重新分发正文。

服务器收到 `delivered` 或 `rejected` 后，若结果/tombstone 尚未双副本提交，只返回“结果已接收，复制待完成”；接收方持续保存并可重发结果，服务器不得据此清理最后正文。恢复双副本后先合并终态、再决定哪些暂存正文需要复制/交付。单副本未送达内容随该节点永久丢盘时，只能从发送方保留的 outbox 重投；不能承诺此时发送端也丢数据仍可恢复。

无多数派或失去主资格：停止正式提交、权威读取及降级接入，返回 `NO_QUORUM`/`NOT_LEADER`。客户端继续本地排队，已有 P2P 若可用仍可直连；不会把少数派当成备用来继续写入。

## 7. 接收事务、ACK 与清理

- 收件端顺序为：验签解密 → 校验内容 → 原子持久化业务结果、去重索引、群状态/文件引用及待发送结果 → 发签名结果。中途重启从持久状态继续。
- 相同 `(sender_key_id, recipient_key_id, envelope_id)` 及 hash 重复到达，返回同一持久结果；不同 hash 隔离并报冲突。P2P 与 mailbox 共用此去重边界。
- `deferred` 不删除服务器正文，不表示业务已应用；客户端有界缓存丢失后可重新拉取。`rejected` 可最终清除坏项，但不能产生 delivered。修复联系人后需要重新发送的，应由明确用户操作产生新信封。
- 正文删除前，结果与 tombstone 必须双副本提交。终态索引至少保存对象键、hash、固定到期时间、结果类型及证据摘要。首版不自动淘汰仍可能关联重试/旧快照的终态索引；配额不足时拒绝新接入，不静默删除去重证据。
- 过期正文的清理由当前有权主节点有序提交；固定 TTL 到期不证明曾送达。单副本降级时，缺乏双副本删除证据可延后清理并触发容量告警；不能为释放空间删除未确认的唯一副本后仍报告可靠保存。
- 管理员恢复过旧备份必须换数据代际并从健康副本重新建库；不得把已超出日志/删除索引保留边界的旧库直接重新服务。清理终态索引的后续方案需另行定义不可重放边界。

## 8. API 与兼容性契约

以下是目标 v2 逻辑接口与字段，当前不存在，不改变 opaque 信封加密格式。规范化 JSON、签名域和测试向量须随实现提交；同名 v1 字段不能偷偷改变语义。

| 接口 | 必需行为 |
| --- | --- |
| `GET /v2/cluster/status` | 返回签名的集群/配置/任期、主角色、节点数据代际、角色、数据/提交水位、就绪与降级原因、有效期和能力；挑战请求需绑定 nonce，静态缓存状态不可单独作为当前主证明 |
| `POST /v2/envelopes` | 验证现有身份和信封授权，增加固定 `not_after`、操作 ID；返回 `storage_state`、`delivery_state` 及可验证提交结果 |
| `POST /v2/mailbox/{recipient_key_id}/pull` | 收件人签名请求；主节点经读屏障返回正文及复制等级；备用返回可信主提示，不能以空列表掩盖未就绪 |
| `POST /v2/mailbox/{recipient_key_id}/results` | 接收逐信封 signed result；明确区分 delivered/deferred/rejected，返回每项结果提交状态 |
| `POST /v2/delivery/status` | 授权查询原操作；区分 replicated、暂存、未知、终态；携带证据，查询未知不是允许换 ID 重发的依据 |
| v2 设备/路由与 intro 对应接口 | 保留原业务权限，采用本协议的提交/冲突/恢复规则，必须协商版本 |

提交结果绑定 `protocol_version、cluster_id、control_generation、config_epoch、leader_term、commit_index、operation_id、sender_key_id、recipient_key_id、envelope_id、envelope_sha256、not_after、storage_state、delivery_state、replica_evidence`，签名证明声明来源；升主有效性还依赖控制面决定，不能仅相信旧主自己的签名。规范编码见主设计 16.10。

收件方结果绑定 `version、sender_key_id、recipient_key_id、envelope_id、envelope_sha256、outcome、reason_code、received_at、result_id、result_sequence`，由收件身份在独立 RecipientResult 签名域下签署。HTTP 外层另绑定 cluster_id/请求 nonce/时间，接收结果本体不绑定某个 VPS 或传输，从而在 P2P/mailbox 间核验复用，不使迁移改变信封 ID。错误必须区分暂时存储故障与确定性坏密文。

错误约定：`NOT_LEADER` 带可信提示但不能引导到未授权 URL；`NOT_READY、NO_QUORUM、REPLICA_UNAVAILABLE` 可退避重试；`ID_CONFLICT、AUTH_FAILED、EXPIRED、UPGRADE_REQUIRED` 不盲目换节点绕过；`RATE_LIMITED` 遵守 Retry-After。采用明确 HTTP 状态与结构化 code，签名状态结果比单独 HTTP 成功更重要。

旧客户端/旧服务不具备 v2 保障。首版发行的双端必须支持 v2；v1 入口可独立保留为旧版有限服务，但不得在同一数据目录上绕过 v2 提交规则。v2 不得静默降级为 v1 后仍显示可靠保存。升级、回滚和成员清单更新必须先测试，不能一次滚动更新造成不兼容任期/目录分裂。

## 9. 客户端切换与恢复参数

客户端持久化主备候选、可信集群配置、最高已验证任期提示、当前活动地址和待投递信封。静态配置签名与动态领导权分开；清单获取成功不能覆盖活动业务地址。仅在同一授权集群内切换，不靠临时 DNS 更新完成故障接管。

首版参数基线：前台活跃会话健康检查间隔 5 秒；连接超时 3 秒；小请求总超时 8 秒；连续两次可重试失败或一次明确主角色变更触发重新解析；失败重试 1/2/4/8/16/30 秒封顶并加入 ±20% 抖动，尝试未失败备用不必等满当前节点冷却。长文件总时限按进度计算，停滞 15 秒触发恢复，重试保持原分片/信封 ID。RTO 以第 11 节实测为准，参数相互配合不能靠缩短安全租约硬凑。

故障后步骤：发现异常 → 验证备用身份与当前主资格 → 等待其应用到安全水位 → 使用本地签名资料重新确认路由 → 查询原 ID 结果 → 必要时重投 → 拉取并重发未确认接收结果。客户端不自行选举主服务器。

恢复节点通过独立身份和新数据代际进入 `recovering`；从一致快照及截断点后的日志补齐，核对终态、hash 和提交水位后成为备用。只有配额、水位和落盘能力合格才恢复双副本确认。用户看到服务恢复不代表已恢复冗余，二者分开显示/监测。

## 10. 故障决策表

| 故障 | 允许行为 | 禁止行为 |
| --- | --- | --- |
| S1 停机，S2+Q 存活且 S2 数据完整 | 仲裁升 S2，自动切换，读旧数据及降级接入；客户端保留新 outbox | 把 S2+Q 算成两份信封副本 |
| S2 停机，S1+Q 存活 | S1 保持主角色，降级接入，继续已有投递 | 新数据返回 replicated |
| Q 停机，S1+S2 健康 | 两个控制投票仍构成多数派，双业务复制继续 | 因 Q 无正文而声称可容忍再失去任一节点 |
| S1/S2 业务链路断开，但控制面有多数派 | 唯一主侧可降级；备用提示主信息 | 双方独立正式提交；无数据链路仍返回 replicated |
| 旧主位于少数派，新侧有多数派且数据就绪 | 新侧接管，旧主隔离写入 | 仅凭旧主进程存活或旧租约缓存继续确认 |
| 无控制多数派或可升主节点数据缺失 | 在线服务显式不可用，本地排队/P2P/离线文件按实际条件可用 | 自动强制升主、重置任期或假报空邮箱 |
| 丢失一个永久业务盘 | 存活副本保留正式数据；替换节点重新建库恢复冗余 | 用旧游标认为空节点已经同步 |
| 两份业务盘均丢失 | 灾难恢复，按备份和客户端副本对账，明确实际 RPO | 宣称属于单节点零丢失保障 |

## 11. 验收指标与实现次序

所有数值是目标，不是已测容量。标准负载、测量起止、故障次数和证据要求以 [验收标准](relay-ha-acceptance.md) 为准。

- RPO：有效期内 replicated 未终结消息在单业务节点永久故障下丢失数 0；错报 delivered 数 0；重复业务应用数 0。
- RTO：具备剩余多数派、完整副本和可达路径时，前台真实双端从注入单节点故障到成功完成一次 4 KiB 消息接收，最长 60 秒。故障持续不满足前置时单独报告，不伪记 60 秒达标。
- 正常双副本保存：标准负载下 4 KiB 消息客户端提交到 replicated 的 p95 ≤3 秒；不含用户接收离线时长。跨境不达标应调整部署/实现，不能降低落盘规则。
- TTL 基线：7 天；服务端持久化固定绝对期限并返回客户端；逻辑重试不续期。临界过期测试用隔离时钟，不移动生产时钟。
- 恢复冗余：标准 1 GiB 恢复数据集、专用测试链路可用吞吐 ≥10 Mbit/s 时，全量恢复+对账 ≤30 分钟；接管与全量重建分别计时。
- 72 小时稳定性：周期故障后持续对账；所有 P0 用例通过；用户试点沿用原计划 7 天，不以本文编写完成算通过。

实施次序：持久状态/结果类型及不变量测试 → 控制面与双副本提交设计/实现 → intro/路由/ACK 原子恢复 → 双端 v2 状态机与切换 → 本地故障注入 → 独立 VPS 与正式双端验收。修改现有同步与状态语义时同步更新手册；不得只修改前端成功文案。

参考依据：[etcd 网络分区与多数派行为](https://etcd.io/docs/v3.6/op-guide/failures/)、[PostgreSQL 同步复制与持久化确认](https://www.postgresql.org/docs/17/warm-standby.html)。HA-D1 已将 etcd 列为待实现选型，PostgreSQL 仅为约束参考；两者文档都不是本项目已达到保证的证据。
