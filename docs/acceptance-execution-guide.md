## 1. 服务器集群实现到什么程度

当前源码已实现“多入口节点池 + 节点身份验证 + 部分业务数据异步同步 + 客户端切换”。每个节点使用自己的SQLite数据库；没有跨节点写入仲裁，产品设计明确不承诺强一致多副本。

| 能力 | 本次源码依据 | 可得出的结论 |
| --- | --- | --- |
| 签名节点清单、节点身份challenge | 服务端路由 `/v1/nodes/manifest`、`/v1/node/challenge`；节点清单/密钥加载校验 | 已有真实实现，仍需实际部署配置和跨主机验证 |
| 节点间同步 | `apps/envelope-server/src/main.rs` 的 `node_sync_push`、`apply_node_sync_push`、`push_node_sync_once` | 同步四类数据：device routes、mailbox envelopes、delivery receipts、ACK tombstones |
| 周期发送与失败重试 | `run_node_sync_worker` | 默认15秒一次，每表每批最多500条；失败不推进该peer游标；15秒是调度默认值，不是收敛时延保证 |
| 持久化同步进度 | `node_sync_peer_state`、`load/store_node_sync_cursor` | 有每peer持久化游标；多页、重启、恢复备份、新节点仍须实测 |
| 节点认证 | `validate_node_sync_push` | 校验来源、撤销状态、epoch、节点有效期、时间偏差及节点签名 |
| 已确认消息删除传播 | `mailbox_ack_tombstones` | 应避免旧副本再次提供已ACK消息；故障与恢复组合须验证 |
| 客户端切换 | Android `android_server.dart`；WPF `EnvelopeServerClient.cs` | 有节点发现/验证/候选节点请求路径；双端真实包切换尚需证据 |
| intro互加会话 | 存于本机 `intro_sessions`；不在NodeSyncPushRequest四类数据中 | 未见intro跨节点复制；不能由mailbox可切换推导intro也无缝切换 |
| `/health` | 返回协议版本和固定OK状态 | 仅证明HTTP处理可达，不检查同步worker、复制积压、数据库业务可用性或集群收敛 |

启用同步至少需要：有效且一致的签名manifest、各节点不同node id及对应私钥、至少一个有效且具备route/mailbox能力的peer、peer地址可达、未设置 `--disable-node-sync`。未配置manifest或本节点身份时，同步worker不会启动；两个普通服务进程不自动构成有效集群。

必须区分以下结论：

1. **源码已实现**：本次检查可以确认上述机制存在。
2. **已有工程测试通过**：见本次服务端测试日志和下方验证记录；只对应已执行的函数/数据库用例。
3. **实际集群已部署并正确配置**：本次尚未检查真实节点，不能确认。
4. **生产高可用验收通过**：尚需跨主机故障、对账、恢复与真实客户端证据，当前不能确认。

典型风险：S1已接受消息，后台尚未复制到S2时，S1永久丢盘；S2可能没有该消息。若客户端没有可重投副本，消息无法仅靠“切换节点”找回。同步周期、网络分区、积压和备份恢复都会改变该窗口。单节点写入成功不能解释为多副本提交成功。

## 2. 如何验证集群

先用本机不同端口、不同数据目录的两个服务进程验证协议和复制，再在两台独立测试主机复验网络分区、主机重启及客户端切换。双本地进程不能模拟独立主机故障域。

所有数据用独立测试身份生成，并通过正式签名请求写入；S1和S2必须分别固定目标，避免客户端自动回退掩盖某节点的数据缺失。可用各节点只读数据库摘要补充验证，不能只调用负载均衡后的统一URL。原始消息正文、恢复词与私钥不入报告。

下表 C-01～12 保留为旧 best-effort 实现的诊断场景，不增加父用例。首版放行改按 HA-01～24 的更严格标准，C 场景观察到的缺失窗口不能作为允许丢失的产品结论。场景尚未执行。技术操作可由Codex编排，真实服务器接入和涉及业务的停机窗口由负责人确定。

| 场景 | 操作 | 通过证据 / 判断 | 对应父用例 |
| --- | --- | --- | --- |
| C-01 启用与身份 | 检查两端版本、不同数据库和node id、相同manifest/epoch；分别challenge并验证签名；确认worker启动及有效peer | 两节点身份与清单一致，真实同步请求成功；/health单独不够 | NET-11、REL-01 |
| C-02 四类数据双向复制 | 固定S1登记route、提交mailbox→直接在S2检查；在S2拉取并ACK→直接在S1检查receipt和tombstone；交换S1/S2重做 | route、envelope id/hash、receipt、删除标记逐项对账；记录端到端复制延迟 | NET-02、NET-12 |
| C-03 已复制后的节点故障 | 先证明S2拥有目标消息→停S1→仅通过S2收取；A/W各做一次→恢复S1 | 用户链路完成，消息只入库一次；恢复后不复活已ACK项 | NET-12、OPS-01 |
| C-04 复制前故障窗口 | 暂停S1→S2同步→S1接受新消息→隔离S1→查看S2；再恢复S1 | 必须量化缺失窗口及恢复/重投结果；不能按强一致标准宣称已有能力。若发布要求任意故障零丢失，此场景未满足即不放行 | NET-12、OPS-03 |
| C-05 双向分区与合并 | 切断两节点互联，各接收独立有效消息和route变化→恢复互联 | 未过期数据按已确认冲突规则收敛；ID/hash对账、去重与ACK状态正确 | NET-12 |
| C-06 大批量与游标 | 每类有效数据超过500条，加入相同时间戳记录→运行多批同步→中间重启发送节点 | 跨页无漏项；游标恢复有效；记录积压清空时间，不能把15秒当固定完成期限 | NET-12、OPS-04 |
| C-07 ACK先到及旧数据重投 | 使tombstone先到目标节点→随后回放旧mailbox副本；另隔离后恢复带旧消息的节点 | 已确认消息不复活；receipt状态不倒退；过期与清理规则可解释 | NET-12、MSG-08 |
| C-08 新节点/备份回退重建 | 新建空S3并经受控清单变更接入；另把S2恢复到旧备份且保留同node id | 检查是否补齐全部未过期数据；特别关注其他节点游标已前移后旧备份是否漏数据。任何需要重置/重建的步骤必须写成运维流程 | OPS-03、NET-12 |
| C-09 认证与清单变更 | 错签名、撤销节点、过期、epoch不一致、时钟偏差；更新清单后按当前加载方式重启必要节点 | 拒绝非法同步；合法清单恢复后可继续；不把启动时加载宣称为已实现动态热更新 | NET-11 |
| C-10 服务配额与资源 | mailbox接近限额，加入大密文及批量复制，测试HTTP body limit、磁盘满、peer慢响应 | 超限可诊断，其他节点不被饿死；游标不错误前进、无静默丢失；观察真实失败重试 | OPS-02、NET-12 |
| C-11 intro跨节点 | 在S1创建intro session→响应/轮询固定S2；再模拟客户端中途切换 | 记录实际行为；未复制session时必须有明确的同节点约束/重新互加回退，或修复后复验；不能以404当无缝成功 | CON-04、NET-12 |
| C-12 真实双端与长期运行 | 最终APK/WPF包分别经不同节点收发；72小时内轮流中断一个节点并恢复 | UI结果、每成员收件集合、节点日志、资源曲线共同证明；试点签署由人负责 | OPS-04、OPS-05、OPS-06 |

首版 RPO/RTO 与标准负载已在主备协议和专项验收中定义：有效期内 replicated 数据单盘故障丢失 0，满足多数派/完整副本/可达条件的前台接管 ≤60 秒。部署参数、容量及告警处置人需在开测前登记；不能以测试测得多少就把多少定为通过。

## 3. 谁来做验收

按“操作执行”和“结果判断”拆分。同一父用例经常同时包含可自动执行的技术步骤与需要人工的系统认证/体验判断，因此不强行把112个父用例都贴成纯自动或纯人工。

### 3.1 Codex可独立执行的技术工作

- 阅读源码、冻结输入清单、生成测试数据和SHA-256、运行现有Rust/Flutter/WPF测试、补齐有价值的集群与故障注入脚本。
- 构建双端候选包、校验版本/依赖/FFI/签名/更新manifest、核查正式APK的bridge开关；签名材料须由用户现有受控配置提供，不把密钥写入报告。
- 搭建隔离的本机多节点环境，发出有效签名请求，验证复制、去重、回执、清理、限流、恶意输入、游标和服务恢复。
- 对可访问的数据副本验证备份格式、身份派生、存储加密、事务、replay与文件哈希；为Android真实SQLCipher测试准备脚本和证据采集。
- 在设备/服务已接入的前提下采集日志、性能、资源和崩溃，做对账、生成缺陷与复验报告。持续72小时任务需要真实持续运行的主机和监测任务，不能在一次短对话里算完成。

### 3.3 当前会话的实际接入边界

已确认本机可找到 `cargo`、`flutter`、`dotnet`、`adb`。尚未核对已连接设备、干净Windows环境或真实集群地址/权限；工具存在不等于目标可访问。

当前提供的CUA接口关闭了原生桌面控制，不能承诺直接自动点击全部WPF验收页面。可另行验证Windows UI Automation等测试工具是否适配产品，补齐后再将对应步骤转为自动；在此之前，WPF底层/控制台验证由我执行，实际UI操作由人配合。Android可通过serial限定的ADB和系统UI证据自动化，仍须先确认设备已授权且测试包/正式包界限清楚。正式APK不能为了方便验收而临时开启测试bridge。

“必须人工”的核心是：真实身份认证和指纹归属、物理环境动作、真实用户体验、业务规则/风险接受与最终签署。其余客观测试尽量由自动化承担；某项暂缺脚本或设备不意味着它本质上只能人工。

## 4. 推荐执行顺序

1. 按主备协议完成控制面/双副本持久提交、v2 结果、幂等及恢复的实现设计，修复现有异步窗口和 intro 缺口；不能直接将旧测试结果作为新功能完成证据。
2. Codex完成本地工程/包检查与 S1/S2/Q 隔离集成及故障脚本，将 HA 不变量做成可复现实例。
3. 在独立故障域 S1/S2/Q、Android 真机和干净 Windows 上执行 24 项 HA 及原产品用例。Codex编排技术测试和对账，将本人认证、物理动作和暂不可自动化的 UI 汇成配合清单。
4. 完成 72 小时运行、真实首次体验和 7 天试点后签署。未执行实例保留在分母中，自动化结果与人工判断均写入统一模板。
