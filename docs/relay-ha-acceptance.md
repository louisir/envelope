# 首版主备中继验收标准

版本：1.1｜日期：2026-09-20｜全部用例：待执行。对齐主设计 HA-D1 和协议 1.1，仍为 24 个父用例。

协议依据：[主备中继协议](relay-ha-protocol.md)。本清单包含 24 个 HA 父用例，是原 [112 项产品用例](acceptance-checklist.md) 的新增发布门槛；首版共 136 个父用例，按实际执行实例计算通过率。旧 VPS-01～VPS-12 属后续发现/选点方向，不再计入首版；C-01～C-12 是旧实现诊断场景，不另计父用例。

## 1. 开测条件

- 冻结源码快照、APK/WPF/服务端和控制面组件版本、全部二进制 SHA-256、协议版本、schema、签名清单、节点身份摘要及配置哈希。工作区未提交输入必须纳入快照。
- 三个独立故障域：S1/S2 为业务副本，Q 为第三控制投票成员；不能把同机三个进程当成跨主机证据。硬件、存储持久化方式、云网络和带宽逐项记录，不从 SSH 能登录推导符合条件。
- 正式 Android 和 Windows 包，各使用独立隔离测试身份；至少执行 A→W、W→A。A→A/W→W 作协议对照，自动化批量负载不替代正式 UI 证据。
- 安全保留 SSH 管理路径，故障注入仅针对隔离部署、测试服务及数据。真实销毁数据先核对目标路径和测试标识；也可通过完全隔离旧盘并在空盘重建模拟永久丢盘。生产现有业务不参与破坏性测试。
- 系统时钟正常时偏差 ≤1 秒，使用单调时钟统计时延。时钟跳变、网络方向、丢包与限速只在隔离环境注入，记录完整开始/结束及恢复动作。
- 协议第 2 节要求的共识组件、提交决定存储、fencing、落盘和恢复适配设计已经完成技术审查并进入候选包；缺失任一项记阻塞，不能以演示心跳切换替代。
- 设计依据为主设计第 16 节；组件精确版本、SQLite FULL 的逐写连接读回、etcd 当前键/历史保留策略及 control_generation 在候选基线中登记。HA-D1 文档完成不表示本条的实现准入已通过。

## 2. 固定负载与时间指标

| 名称 | 配置 / 计算方式 | 门槛 |
| --- | --- | --- |
| L1 正常收发 | 20 个独立身份，10 条/秒共 30 分钟，每条业务明文 4 KiB，收件端及时领取；先预热 2 分钟不计样本，双向均匀分配 | replicated 确认时延 p95 ≤3 秒；非注入阶段成功率 ≥99.9%，最终有效消息全部对账，无丢失/假确认/重复业务应用 |
| L2 故障探针 | 每秒提交一条 4 KiB 消息，前台真实双端同时有在途操作；故障前已完成双副本同步 | 每次故障注入至存活侧首次完成新的端到端接收 ≤60 秒；重复 ≥10 次，报告每次及最大值 |
| L3 积压恢复 | 固定数据集：1 GiB 有效恢复数据，含至少 1000 条信封、各类结果/终态/路由/intro；测试配置允许该容量 | 实测链路吞吐 ≥10 Mbit/s 的前提下，重建至可作第二副本并全量对账 ≤30 分钟 |
| L4 文件/群组 | 在线文件边界沿用产品 64 MiB、4 MiB 分片；混群至少 5 个成员、各自唯一身份 | 全文件 hash 一致；每收件人及逻辑消息单独对账，不按 HTTP 请求数推定群发成功 |
| L5 长期运行 | 72 小时：至少 2 条/秒 4 KiB 业务消息，每小时一轮小文件；每 6 小时轮换注入一次单节点/链路故障并完全恢复后再进入下一轮 | 所有正式确认消息按有效期和签名结果对账，24 个 HA 父用例全通过；无开放 P0/P1 缺陷 |

L2 的自动恢复时限只适用于剩余多数派、完整业务副本和可达客户端路径存在。无多数派的测试考核“及时停止错误服务并保留待发”，不使用不可能恢复的时间段统计可用 RTO。Android 后台休眠另记录，不能把前台结果宣传为息屏实时到达。

L1/L5 的实际请求量须落在冻结的候选部署限额内：可分布测试来源，或提前登记足够的生产配置限额（例如 L1 单来源压测至少 1200 次提交/分钟以覆盖重试余量，单身份至少 60 次/分钟）。不关闭鉴权/限流，也不把调高后的配置性能声称为旧默认 120 次/IP/分钟下的结果。限额边界仍由 HA-20 单独验证。

记录 p50/p95/max、失败和未完成数，不能剔除超时样本后只报告成功请求时延。大文件计整体完成时间与恢复位置，不用 4 KiB 消息阈值判定文件总耗时。CPU/内存/磁盘/队列/电量曲线必留，正式支持规模及设备预算在执行前冻结；不因测试后失败再降低负载。

## 4. 提交与接收故障切点

HA-03/HA-09 每个切点至少 10 个独立消息实例，覆盖两端及主角色互换；在隔离测试版本加入精确故障钩子，然后用正式候选包重做可外部复现的端到端场景。测试钩子包与正式包哈希分开。

| 切点 | 应观察到的结果 |
| --- | --- |
| 本地 outbox 提交前 / 后 | 前者不能显示已排队；后者恢复原消息 |
| 主业务数据落盘前 / 后 | 没有双副本/决定只能 pending 或 staged |
| 备用持久化前 / 后 | 后者仍不等于正式提交，不能缺少控制决定 |
| 控制面提交决定前 / 后 | 前者不正式可见；后者可恢复、应用，不能丢决定 |
| 主应用后 / 响应发送前后 | 丢响应后同 ID 恢复原结果；已 replicated 可在备用恢复 |
| 备用准备完成 / 尚未应用 | 新主必须先应用至提交水位，不能读取缺失或跳过记录 |
| 收件内容/文件持久化前后 | 之前无 delivered，之后去重并可补发结果 |
| 接收结果记录后 / tombstone 双副本提交前后 | 未双副本时不清理最后正文；完成后旧副本不能复活 |

## 5. 对账、指标证据与签署

建立单一受控测试清单，每条记录含 sender/recipient key ID 摘要、逻辑消息与 envelope ID、hash、固定到期时间、发送端持久化时间、实际路径、提交证据、收件方签名结果、UI 终态。群组与文件同时记录子信封及上层逻辑 ID。

数据集合：E=测试清单期望对象；R=带有效 replicated 证据且当时未过期对象；D=带有效收件签名且客户端持久化对账成功对象；J=确定拒绝对象；X=已确认过期对象；P=仍待确认对象。每个对象按最新可验证证据得到唯一业务结果，R 是存储属性，不与 D/J/X/P 混作互斥状态。

- 单盘故障后，R 中每个未终结、仍有效对象必须存在于存活副本或可应用的正式日志中；少一条即失败。
- 宣称 delivered 的对象必须在 D；UI delivered 数不大于且最终等于对应有效 D，不能用服务器 ACK 数替代。
- E 中每个有效收件对象的业务应用次数为 0（未完成/拒绝/过期）或 1（完成）；网络尝试次数可以大于 1。
- P 不能从通过率分母消失；测试结束必须完成投递、明确到期/拒绝，或将关联用例标记未完成。坏信封测试的期望拒绝不计合法消息丢失。
- 各副本在相同提交截点比较规范化业务摘要；排除节点本地运行统计，包含终态索引、会话、对象版本和固定 TTL。

证据目录建议 `artifacts/acceptance/<run-id>/ha/`，包含候选清单、脱敏配置、故障编排与恢复日志、逐消息 JSONL、双端 UI、实际路径证据、提交/副本摘要、结果统计、CPU/内存/队列/空间曲线及 SHA-256。日志不含恢复词、私钥或真实聊天正文。本地 artifacts 被忽略，正式签署前归档至受控团队位置。

Codex 可编写协议驱动测试、故障编排、包/日志/摘要校验和统计；真机接入、个人系统认证、物理操作及正式 UI 暂无法自动化的步骤由人配合；真实用户试点与发布签署由负责人完成。不能把没有执行环境标成不适用后放行。

放行：24 个 HA 父用例全部通过，原 112 项按既有 P0/P1/P2门槛通过，适用参数实例无失败/阻塞/未执行，支持规模/网络及降级语义与手册一致。协议参数修改必须升版本并重跑受影响实例，不在失败后追溯修改预期。执行记录使用 [统一模板](acceptance-run-template.md)。
