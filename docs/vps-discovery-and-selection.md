# VPS 发现与客户端选点需求

日期：2026-09-20。状态：后续版本方向，已移出首版发布范围；尚未实现或验收。后续对话将首版收敛为 [VPS 主备中继协议](relay-ha-protocol.md) 与 [主备验收标准](relay-ha-acceptance.md)，两者优先。本文保留早期发现与选点设计，VPS-01～VPS-12 不计入首版验收，不应据此启动 DHT、客户端目录传播或动态选点改造。当前实现仍以 [设计基线](design.md) 为准。

## 1. 后续版本候选范围

- VPS 承担第三方通信中转及服务端职责；客户端不提供第三方中继、代存邮箱或服务端副本。
- 客户端维护自己的 VPS 目录，根据自身链路算法选择适合当前网络和业务的 VPS。
- 目录可由任意可信 VPS 或其他客户端提供更新，不依赖唯一入口或首次配置的服务器。
- 配置地址承担引导作用，不强制成为长期业务地址；有有效目录时选点不需要主入口在线批准。
- Android 与 Windows 使用一致的目录验证、选点和切换规则。

本次收敛取消前面讨论的“客户端贡献节点”方向，不将其列入实现计划。现有双方直接 P2P 通信不等于替第三方中转，本需求不据此删除现有直连能力。

用户类比的 BT DHT 是分布式发现机制。此次采用其多来源发现、本地维护和持续更新的思路；不要求兼容 BitTorrent 公共 DHT、实现 Kademlia，或把客户端变成公共服务端。[BEP 5 官方规范](https://www.bittorrent.org/beps/bep_0005.html)

## 2. 节点目录与信任

目录来源包括配置入口、内置备用入口、已知可信 VPS、已有客户端通信通道和持久化缓存。任何一个来源都可以带来更新；更新由接收端验证后落地，远端不能直接改写本地数据库。

必须区分三类信息：

| 信息 | 更新依据 | 处理原则 |
| --- | --- | --- |
| VPS 身份、地址、能力、加入和撤销 | 受授权签名的目录 | 验签、版本检查、有效期检查后接受 |
| VPS 容量、维护与就绪状态 | 已认证 VPS 发布的有时效状态 | 作为短期准入/选点依据，过期失效 |
| 本机延迟、成功率、超时与失败冷却 | 本客户端的实际测量 | 本地维护，其他节点不能覆盖 |

第一版建议复用现有 `NodeSetManifest`，任意可信 VPS 和客户端均能转发完整签名目录。可信“业务节点”身份不自动赋予它修改全网成员目录的权限。如果需要多个 VPS 独立签发目录，须另行定义发布者授权、作用域和冲突规则，不共用根签名私钥，也不靠不同发布者的最大版本号解决冲突。

目录接收规则：

1. 限制消息大小、节点数及处理频率，验证受信任签名、目录 ID、协议格式与有效期。
2. 持久化每个受信任目录的最高已接受 epoch 及内容摘要；低版本不覆盖，高版本原子更新，同版本同内容去重，同版本不同内容视为冲突并保留已验证状态。
3. 完整目录按版本替换授权集合，不把不同版本条目任意合并，避免恢复已撤销节点。`prev_manifest_hash` 的跳版本校验及缺失链补取规则应在协议实现前明确。
4. 缓存目录与本地链路统计分开保存；重启不会丢失已知节点和防回滚状态。
5. 新节点验证身份、地址、兼容性和业务就绪后才进入可选集合；撤销节点停止新请求并按恢复流程迁移。
6. 已过期目录不能因为来自熟悉客户端就自动延长信任。目录需在有效期内续发；多来源传播不能保证实时获得撤销信息，需明确失联后的可用性边界。

“从任意来源更新”不等于“接受任意地址”。第一版公开目录只接受受授权的公网 HTTPS 服务地址，并验证实际目标与重定向；客户端不会因未验证的 peer 推荐而探测任意内网或本机地址。传输只包含公共 VPS 目录，不包含联系人、聊天内容或客户端身份清单。

## 3. 目录传播与刷新

建议使用“摘要通知、按需取完整目录”的方式：先交换目录 ID、epoch 和摘要，遇到更新再请求正文。正文可来自可信 VPS，也可来自已有客户端通道；经 VPS 转送的客户端目录通知仍属于目录交换，不是客户端为第三方提供中继。

刷新周期独立于签名有效期：启动、周期到期、网络切换、当前节点失效或收到更新通知时触发有限刷新，附带退避、抖动与去重。不能继续把“距过期五分钟”当作唯一更新时机，也不能收到通知就立刻切业务节点。

新增 VPS 流程：部署和身份配置 → 目录授权发布 → 多来源传播 → 客户端验证发现 → 节点数据就绪 → 纳入选点。配置入口不在线时，只要客户端还能访问某个有效 VPS 或已有 peer 通道，就应能获取更新。

首次安装无缓存、所有引导地址不可达且没有 peer 连接时，仍无法自动发现网络；保留多个引导地址和导入签名目录的恢复途径。所有目录交换若都依赖已经不可达的 VPS，不能假设它能自行解除连接依赖。

## 4. 客户端选点

“最优”指根据本机近期观测选择综合更合适的节点，不承诺全球或实时最优。延迟必须从客户端测量，不能直接使用入口到节点的测量结果。

建议算法顺序：

1. 硬过滤：可信、有效、能力匹配、身份验证通过、可达、未处于拒绝准入/维护状态，并满足操作的数据就绪条件。
2. 综合评估：近期业务成功率、平滑 TLS/API 延迟、超时率、节点容量提示、失败历史、现有会话保持及迁移成本。吞吐仅依据实际业务或有限测试，避免主动大流量测速。
3. 在表现接近的少数候选中按容量加权随机选择，分散流量，保留有限探索机会；不让所有客户端确定性地选同一第一名。
4. 节点确认接入后设为活动业务节点；若拒绝接入，退避并尝试其他合格候选，不立即循环重试。
5. 健康节点保持使用；故障、撤销、维护或持续显著改善时切换。使用最短驻留、失败冷却和抖动，避免频繁迁移。

本地状态至少包括引导地址、可信目录、活动业务节点、备用候选、按网络环境区分的测量统计，以及重试/迁移中的操作状态。网络切换后旧统计降低权重。Android 的探测并发、周期和后台行为须考虑电量与流量。

权重、探测频率、超时、最短驻留和切换门槛属于待验证参数，双端使用统一测试向量；先以少量节点验证，再调参扩容。

## 5. 服务端与数据切换条件

每个 VPS 可以发布目录、反馈自身状态并承接符合能力的业务。引导和业务角色可部署在同一 VPS，但获取目录不能改变当前活动业务地址。

当前异步复制覆盖路由、邮箱信封、回执和 ACK tombstone；互加好友会话尚未复制。选点实现必须一起验证跨节点收发、会话归属、超时重试幂等，以及写入尚未复制时的恢复。仅选择低延迟 VPS 不能证明消息可靠性。

当前服务端 manifest 在启动时加载，节点同步要求 epoch 完全相等。上线前需实现明确的目录重载/协调发布及滚动兼容策略，或安排有边界的协调更新；不能将客户端能接收新清单等同于整个集群已完成扩容。

负载就绪探测需覆盖数据库、磁盘和队列水位、同步状态、协议兼容和维护状态；固定返回 OK 的 `/health` 不足以作为准入条件。已有客户端和旧协议兼容性要纳入部署计划。

## 6. 实施顺序与补充验收

实施顺序：先定义目录交换与本地状态协议，再实现两端目录持久化/验证和选点，随后补齐服务端就绪与跨节点恢复，最后执行真实双端、多 VPS 验收。当前不部署八台全量集群，不加入客户端第三方中继能力。
